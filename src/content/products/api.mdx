Every Qubic query depends on a data path: which peers answered, whether their records were checked, and how much history the index keeps. Glyph API runs that path for you and exposes the result over HTTP.

The public API is at `https://api.glyphq.org`. It connects to Qubic peers over TCP, verifies what they return, stores normalized history in ClickHouse, and serves reads from the verified store.

## The data path

The service starts with peers. It receives ticks and the records that come with them over the native TCP protocol, checks quorum vote groups, and writes a tick only after it reaches a verification tier.

<FeatureList
  items={[

ClickHouse holds the normalized history. The API reads that store and returns resources for identities, transactions, ticks, tokens, contracts, and network status. The same store supports analytical queries that would be slow against a live peer.

The index starts at the current epoch on its first run and moves forward. It catches up within that epoch, follows the live network, and serves reads while ingestion continues.

## Query the public API

The health check and status endpoints are a quick way to confirm the service is reachable:

```bash
curl -sS https://api.glyphq.org/healthz
curl -sS https://api.glyphq.org/v1/status
curl -sS 'https://api.glyphq.org/v1/ticks?epoch=240&limit=25'
```

The OpenAPI document is at `https://api.glyphq.org/openapi.json`. The API reference is at `/docs`, and `/status` includes the live service view.

<Callout type="note" title="Ingest is the trust boundary">
  The service verifies peer data before writing it. Once a tick is in ClickHouse, the read path serves it without repeating the peer check. Queries read the verified history rather than a live peer response.
</Callout>
